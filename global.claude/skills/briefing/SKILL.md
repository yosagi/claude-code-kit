# briefing スキル

セッション開始直後に実行することを想定した、現状整理と優先順位の提示。
**読み取り専用**。ファイルの作成・編集・移動は一切行わない。
inbox の本文は読まない（読むと既読化の整合が崩れる。INDEX のファイル名から推定する）。

## 手順

### 1. 情報源を読む

すべてプロジェクトルート基準の相対パス。存在しないものはスキップする。
セッション開始時に自動読み込みされたもの（work_in_progress.md、work_history.md、各 INDEX.md）が
コンテキストに既にあるなら再読しない。

| 情報源 | 読む範囲 | 目的 |
|--------|----------|------|
| `work_in_progress.md` | 全文 | 進行中の作業、中断理由、再開時の残タスク、外部待ち |
| `reports/inbox/INDEX.md` | 全文 | `[NEW]` の件数と、ファイル名（`YYYY-MM-DD_from_<送り元>_<件名>.md`）から送り元・件名を推定 |
| `reports/todos/INDEX.md` と各ファイル | 全文 | 優先度（ファイル名の high/mid/low）、内容、実装ログ参照の有無 |
| `reports/ideas/INDEX.md` と各ファイル | 概要セクションまで | 温めているもの。優先度判定の下位候補 |
| `reports/memory/work_history.md` | 直近3エントリ | 前回何をして、どこで終わったか |
| wip が参照する実装ログ（`reports/tasks/...`） | 末尾30行程度 | 最新の進捗と完了報告の有無 |
| `git status --short` | 出力全体 | 未コミットの差分（コミットはユーザーが手動で行う運用のため、忘れ物になりやすい）。sandbox 内実行時にプロジェクトルートへ生える dotfile 群（`.bashrc` `.profile` `.gitconfig` 等）は sandbox 由来の一時物なので無視する |
| `reports/briefing/*.md` | 全文 | プロジェクト固有の確認観点（下記 1b） |

### 1b. プロジェクト固有の観点を評価する

`reports/briefing/` にあるファイルは、そのプロジェクトが「セッション開始時に確認したい観点」を1観点1ファイルで書いたもの。
各ファイルは「確認」「判定」「提示」の3節を持つ。

```markdown
# 観点名

## 確認
読み取り専用の手段（実行するコマンド、見るファイル）

## 判定
結果をどう読むか（正常 / 要対応の条件）

## 提示
どの分類（進行中 / 新着・返答待ち / 外部待ち / 控え / 優先の提案）に載せるか、要対応のときの次の一手
```

ファイルごとに「確認」を実行し、「判定」に従って結果を読み、「提示」の指示どおりに手順4の該当セクションへ載せる。
正常と判定された観点は提示に含めない（何も無いことを報告しない）。
「確認」が sandbox の制約で失敗したら、その旨を添えて「確認不能」として提示する（2b と同じ扱い。sandbox を外しての再実行はしない）。
ディレクトリが無ければこの手順はスキップする。

### 1c. insight の状況を確認する

`reports/insight/` が存在するプロジェクト（insight を使っているプロジェクト）では、insight-status スクリプトを実行する。

```bash
~/.claude/skills/insight-status/insight-status.sh <プロジェクトルート>
```

出力の読み方と手順4への反映:

- **未レビュー N 件**（`Review 結果` 節のないレポート）→ 「新着・返答待ち」に「insight 未レビュー N 件 → `/insight-review`」として載せる。
  inbox の `[NEW] ..._from_insight...` と同じものを指しているので二重に数えない
- **レポートなし → 失敗の疑い** → 「優先の提案」の先頭に、`journalctl --user -u insight-<unit>.service` で原因を見ることを一手として載せる
- **完了記録なし** → 前回発火から数時間以上経っていれば上と同じ扱い。直近なら走行中として「外部待ち」
- **Phase 0 スキップ** → 活動がなければ正常。何も載せない
- 次回予定は、提示の末尾に一行あれば十分（「次回 insight: 9/13 (日)」程度）

`reports/insight/` が無ければこの手順はスキップする。

### 2. 分類する

読んだ内容を以下の4つに振り分ける。

- **進行中**: wip に記載があり、再開すればすぐ手が動くもの
- **新着・返答待ち**: inbox の `[NEW]`。他プロジェクトが返事を待っている可能性がある
- **外部待ち**: 自分からは動けないもの（他プロジェクトへの依頼の返信待ち、実験・ジョブの完了待ち、ユーザーの判断待ち）。wip の「待ち:」「走行中」等の記述や TODO 本文から拾う
- **控え**: TODO と IDEAS。着手条件が揃っているか（依存する作業が終わっているか、判断材料が揃っているか）を見る

### 2b. 外部待ちの現況を調べる

待っているものが「まだ待ちか、もう動けるか」は briefing の時点で確かめる。
待ちの種類ごとに、プロジェクトが把握している手段で現況を取る。

- **他プロジェクトへの依頼の返信待ち**: wip に「X へ送信（日付）」とあれば、`reports/inbox/INDEX.md` に
  `from_X` でその日付より新しいエントリがあるかを見る。あれば「返信が届いている」、なければ「返信まだ」
- **実験・ジョブ・ビルド等の完了待ち**: プロジェクト内に状態確認の手段（既知のスクリプト、CLI、KB や
  実装ログに書かれた確認手順）があれば実行して結果を添える。wip に `確認:` 行でコマンドが
  書かれていればそれを優先する。手段が分からないものは推測で組み立てず「待ちのまま」と提示する
- **ユーザーの判断待ち**: 調べようがないので、判断を求める形で提示する

実行するのは読み取り専用の確認のみ（enqueue / dequeue / 削除 / 再起動などの状態変更は briefing では行わない）。
確認コマンドが sandbox の制約（ネットワーク到達不可など）で失敗したら、その旨を添えて待ちのまま提示する。
sandbox を外しての再実行や承認要求は briefing からは行わず、必要なら excludedCommands への登録を提案する。

wip に書かれた完了見込み時刻と現在時刻を比べ、見込みを過ぎているものは確認を優先する。
確認結果が「完了」で、wip に次の一手（「完走なら → 答え合わせ」等）が書いてあれば、
それを「進行中」の最初の一手として提示に繰り上げる。

### 3. 優先順位を付ける

以下を土台に、状況を見て調整する。理由を一言添えられないものは順位を付けない。

1. inbox の `[NEW]` — 相手が待っている。まず `/inbox read` で中身を確認するのが最初の一手
2. wip の進行中作業 — 文脈がまだ温かいうちに進めるのが効率的
3. TODO high → mid → low
4. IDEAS — 提案するのは「固まってきた」と判断できるものだけ

調整の観点:
- **外部待ちは下げる**。自分の手が動かせないものは「待ちのまま」と明示する
- **停滞期間**。wip で「塩漬け」「数日寝かせる」と書かれたものは、寝かせた期間が意図の範囲内か確認する（明記された期間を大きく超えていれば再開を促す）
- **未コミット差分**があれば、作業に入る前の片付けとして先頭に置く
- **プロジェクト固有の観点（1b）や insight の失敗（1c）で要対応になったもの**は、その観点ファイルの「提示」の指示に従う。指示が無ければ「相手が待っているもの」の次に置く
- **時間帯**。UserPromptSubmit hook が通知する現在時刻が 0:00〜2:00 なら新規着手を勧めず、残作業の TODO 化や翌日送りを提案する。2:00〜6:00 ならセッション終了処理を勧める

### 4. 提示する

構造化文章モードで、**画面1枚に収まる量**で書く。詳細は各ファイルへの参照で済ませ、本文を転記しない。

```markdown
## 進行中
- （項目）— 現状一言。再開時の最初の一手。参照: `パス`

## 新着・返答待ち
- inbox [NEW] N件: （送り元: 件名の推定）… → `/inbox read` で確認
- insight 未レビュー N 件（YYYY-MM-DD, …）→ `/insight-review`

## 外部待ち
- （項目）— 誰の何を待っているか。確認した現況（完了 / 走行中 @進捗 / 返信まだ / 確認不能の理由）

## 控え（TODO / IDEAS）
- TODO high: …
- TODO mid: …
- IDEAS で固まりつつあるもの: …（なければ省略）

## 優先の提案
1. （項目）— 理由
2. （項目）— 理由
3. （項目）— 理由
```

該当のないセクションは省略する。最後に、どれから着手するかをユーザーに一言で問う。
ユーザーが選んだら、その項目の参照ファイルを読んで作業に入る（この時点で briefing の役目は終わり）。

## やらないこと

- ファイルの編集・移動・作成（TODO の done 移動、INDEX の更新、wip の書き換えを含む）
- 外部システムの状態変更（ジョブの投入・取り消し、サービスの再起動など）。確認は読み取りのみ
- `/insight-review` の開始（insight-status は状況を見るだけ。review はユーザーが選んでから）
- inbox 本文の Read（既読化は `/inbox read` の責務）
- 各ファイル内容の長い引用。参照パスで代替する
- stocktake のような棚卸し分析（実装済み検出・重複統合・長期停滞の網羅）。それは `/stocktake` の責務
