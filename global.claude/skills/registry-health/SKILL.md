# registry-health スキル

`claude-registry` の健全性を検査し、出力を読んで要対応のものだけを提示する。
検査ツール本体は `~/.claude/scripts/check_registry_health.py`（全ホストに配布済み）。

## 呼ばれ方による分岐

このスキルは二つの経路から使われる。**最初にどちらかを判定し、以後その分岐に従う。**

- **対話セッション**: ユーザーが `/registry-health` と打った、または会話で registry の状態確認を
  求めた場合。結果を提示し、要対応があれば次の一手を提案する。修復（`--fix`）は
  ユーザーの承認を得てから実行する
- **insight のローカルジョブ（headless）**: `reports/jobs/` の registry health ジョブとして
  呼ばれた場合。結果を insight レポートの提案に載せるところまでで終わる。
  **`--fix` を実行しない。ユーザーに確認を求めない。** 応答する相手がいないため、
  承認を待つ手順は無応答のまま時間切れになる

以降の「手順」と「出力の読み方」は両方に共通する。違うのは最後の一手だけで、
対話では提案して承認を得る、ジョブではレポートに書いて終わる。

## 手順

1. 引数なしで実行する

   ```bash
   ~/.claude/scripts/check_registry_health.py
   ```

   既定の `--since last` が状態ファイル `~/Notes/claude-registry/<host>/registry_health.json` と
   突き合わせ、前回チェック以降の差分を出す。状態ファイルの更新に registry への書き込みが要るため
   sandbox 外で実行される（`setup_global.sh` が `sandbox.excludedCommands` と
   `permissions.allow` の両方に登録している）。単独の Bash 呼び出しで実行する。
   パイプ・リダイレクト・`;`・`&&` と連結すると excludedCommands に合致せず sandbox 内で走り、
   状態ファイルの書き込みで失敗する

2. 出力は7節構成。下の「出力の読み方」に従って、報告に値するものだけを拾う

   [1] `_log.json` 欠損、[2] digest 無しで終わった対話セッション（参考値）、[3] 旧形式レコードの新顔、
   [4] 壊れたファイル / meta の無い log、[5] ホストの鮮度、[6] バックアップ停滞、[7] journals の会話ログリンク

3. 拾ったものに**どのホスト・どのプロジェクトか**と**次の一手**を添えて提示する。
   異常がなければ「registry 健全（meta N 件 / log N 件、全 N ホスト）」の一行で済ませる

## 出力の読み方

### 報告するもの

- **[1] の「新規」**: 前回チェック以降に発生した `_log.json` 欠損。自ホスト分か他ホスト分かを明記する。
  自ホスト分は `--fix` で復旧できる見込みがある（ただしトランスクリプトの保持期間を過ぎていれば不能）
- **[3] の新顔**: 旧形式のレコード（`agent-*`・start/end のみ・退化レコード）は 2026-04-15 で
  止まっているはず。新しい日付のものが出たら新種の書き込み失敗を疑う。**0 件でないなら必ず報告する**
- **[4] の壊れたファイル**: `.tmp.<pid>` の残骸は書き込みが途中で死んだ痕跡。0 バイトも同様
- **[5] のホスト鮮度**: 「停止?」が付いたホストは、Syncthing の同期停止か、そのホストで
  hook / ccexport が動いていない可能性。前回から新しく停止判定になったホストを報告する
- **[6] のバックアップ停滞**: セッションは続いているのにバックアップだけ止まっているプロジェクトは、
  SessionEnd hook の不調を示す（2026-08-28 の lab-mjlab と同じ形）
- **[7] の journals リンク**: `Unfixable` が前回から増えていれば報告する。`Fixable` があれば
  `check_journal_links.sh --fix` で直せる旨を添える

### 報告しないもの（ノイズ）

- [1] の「継続」分と legacy の件数。既知として状態ファイルに記録済みで、毎回同じ数が並ぶだけ
- [1] の「復旧不能」件数。`--fix` を試みて会話ログが残っていなかったもので、打つ手はもう無い。
  ただし**件数が前回から増えていれば**、新たに保持期間切れを起こした欠損があるということなので報告する
- [2] の絶対値。work-logger を回さずに閉じたセッションの統計であって故障ではない。
  ただし**特定のプロジェクトで前回窓より目立って増えている**場合だけ、その旨を一行で触れる

### 次の一手

- 自ホストの log 欠損 → 「`--fix` を実行する」（下記「修復」へ）
- 他ホストの log 欠損 → 「そのホストで `--fix` を実行する」。**このホストからは直せない**
- ホスト鮮度・バックアップ停滞 → 「そのホストの hook / 同期の確認」
- 壊れたファイル・旧形式の新顔 → 「書き込み経路の調査」（TODO 起票の候補）
- journals の `Fixable` → 「`check_journal_links.sh --fix`」

## 修復（--fix）

**対話セッションでのみ、ユーザーの承認を得てから実行する。** ジョブから呼ばれた場合は実行しない。

```bash
~/.claude/scripts/check_registry_health.py --fix
```

実行前に伝えること:

- 直せるのは**自ホスト分の欠損 `_log.json` だけ**。他ホストのものは対象外で、そのホストで実行する必要がある
- 会話ログ（`~/.claude/projects/**/*.jsonl`）が残っていないセッションは再生成できない。
  その場合はセッションの隣に**復旧不能マーカー**が置かれ、以後の一覧から外れる。
  状態ファイルはホスト別で他ホストから読まれないため、判断を共有するにはセッションと同じ場所に置く必要がある
- 内容を先に見たい場合は `--dry-run` を付ける

## やらないこと

- ジョブから呼ばれたときの `--fix` 実行と、ユーザーへの確認
- 承認なしの修復（対話時も同じ。`--dry-run` は承認なしで実行してよい）
- 復旧不能マーカーの付いたセッションの掘り返し（必要なときだけ `--retry-unrecoverable`）
- 検査ツール本体の改修。正本は `dist/scripts/check_registry_health.py`
